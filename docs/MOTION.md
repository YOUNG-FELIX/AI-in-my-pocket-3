# 云台平滑度

**结论先说**：Pocket 3 的云台**原生没有缓动**。单条绝对指令瞬间到位，固件不插值。
所以「丝滑」必须靠外部逐帧下发目标位置。下面是踩坑踩出来的参数，直接抄。

---

## 最优参数

```python
CONTROL_HZ = 60        # 控制频率
LEAD       = 0.0       # 前导补偿，必须为 0
SPEED      = 12.0      # 度/秒
DEADBAND   = 1.5       # 死区阈值（度）
```

`p3server.py` 里就是这四个常量。

---

## 为什么是这几个数

### 控制频率：60 Hz（不是 30）

30° 行程 @12°/s，扫不同频率测画面位移的变异系数（cv，越低越平滑）：

| 频率 | cv | 平均位移 | 标准差 | 完全不动的帧 |
|---|---|---|---|---|
| 30 Hz | **1.179** | 11.54 px | 13.60 | 26/168 (16%) |
| **60 Hz** | **0.190** | 9.70 px | 1.85 | 25/168 (15%) |
| 90 Hz | 0.199 | — | — | — |

**60Hz 比 30Hz 平滑 6.2 倍。** 90Hz 没有额外收益。

**机制**：视频帧率是 30fps。控制采样率若低于视频帧率，云台运动在画面里就变成阶梯。
必须比视频帧率更快地下发。

### 前导补偿：0（推翻了直觉）

直觉上让目标位置超前于当前位置一点（lead），可以避开死区。30Hz 时代确实有效：
「+2° 前导，cv 0.48」。但 60Hz 下完全反过来了：

| lead | cv |
|---|---|
| **0.0** | **0.155** ← 最优 |
| 1.0 | 0.232 |
| 2.0 | 0.189 |
| 3.0 | **0.897** ← 明显变差 |
| 4.0 | 0.808 |

**60Hz 下前导反而有害。** 这是个反直觉但可复现的结果。

### 速度：12°/s

| 速度 | cv |
|---|---|
| 8 °/s | 0.318 |
| **12 °/s** | **0.157** |
| 20 °/s | 0.217 |
| 40 °/s | 0.245 |

最优带大约 **20–60°/s** 的区间里 12 是最低点。太慢反而更顿（见下）。

---

## 硬件限制：慢速必然顿挫

这是**硬件分辨率到顶**，不是代码问题，别再优化了。

### 死区（滞回）

Pan 轴相对当前位置有约 **1–1.5° 的滞回**（典型伺服防抖）：

| 从 0 出发移动 | 画面位移 | 判定 |
|---|---|---|
| 0.25° | 0.02 px | 不动 |
| 0.5° | 0.03 px | 不动 |
| 1.0° | 0.04 px | 不动 |
| **1.5°** | **7.53 px** | **开始动** |
| 2.0° | 15.00 px | |
| 2.5° | 14.54 px | |
| 3.0° | 21.46 px | |

累积 0.25→0.5→0.75→1.0 的结果和直接 1.0 完全一样，**说明不是累积问题，是「离当前位置太近就被吃掉」**。

### 量化

有效分辨率 ≈ **1°**，约 **19.5 px / 度**（@1280 宽画面）。

### 后果

**超过 6 秒摇 30° 必然顿挫。** 五种策略实测（30° 行程）：

| 策略 | cv | 顿挫帧比例 |
|---|---|---|
| 线性 30Hz | 0.51 | 19% |
| 线性 60Hz | **0.19** | — |
| 6 秒慢摇 | 0.55 | 18% |
| ease-in | 0.73 | 29% |
| **12 秒超慢摇** | **1.06** | **48%** ← 一半的帧几乎没动 |

⇒ 越慢越难平滑，因为每帧的目标位移已经低于硬件分辨率。

## 验收口径

**用这些**：
- 列均值互相关（整数位移估计）
- LK 光流（`cv2.calcOpticalFlowPyrLK`）

**别用**：`cv2.phaseCorrelate` 测 mp4 会给出**假结果**（mp4v 重编码 + 归一化问题），
测出「97% 帧停滞」但实际是连续的。这是个坑。

参考数据（40° 行程 @12°/s @60Hz，214 帧 1080p）：

| 指标 | 值 |
|---|---|
| 完全相同的相邻帧 | 0 / 213 (**0%**) |
| 列均值互相关 cv | 0.202 |
| LK 光流 cv | **0.082** |

## 一个关键语义：控制会话的生命周期

不同通路行为完全不同，搞错了会以为「命令没生效」：

| 通路 | 流关闭时下发指令 |
|---|---|
| **DirectShow `IAMCameraControl`** | ✅ **生效**，无需视频流 |
| WinRT `MediaCapture` | ❌ 不累积、不生效；必须流先活着 |

**本项目用 DirectShow**（`p3server.py` 里 `IAMCameraControl`），所以不需要常驻视频流也能控云台。
但注意：视频流和控制是两个独立句柄，服务里两者都开着。

## 为什么不重造人脸追踪

Pocket 3 **原厂自带 ActiveTrack**（人脸/物体跟随）。本项目的 `track` 工具是**软件实现**，
因为原厂的在 UVC 模式下不可达（vendor Extension Unit 在 Windows 被拒）。

所以：
- 想要原厂的稳 → 用机身菜单开 ActiveTrack
- 想要 AI 自己决定看哪 → 用 `look` / `look_rel`

别把软件追踪当成原厂的。README 里标注了这一点。
